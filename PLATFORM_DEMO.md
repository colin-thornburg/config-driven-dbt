# Platform Entity Designer - dbt Architecture

This document explains how the **Platform Entity Designer** frontend interacts with the dbt project to create config-driven data pipelines.

---

## Overview

The Platform Entity Designer is a visual tool that generates dbt models and configurations without requiring users to write SQL or YAML manually. It demonstrates a "config-driven" approach where:

1. **Users design entities** through a web UI
2. **The API generates** dbt model files (`.sql`) and schema definitions (`.yml`)
3. **dbt macros** automatically inject platform control fields (SCD tracking, lineage, CDC)
4. **Changes are committed** to git for version control

```
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│   React UI      │ ──── │   Express API   │ ──── │   dbt Project   │
│  (Frontend)     │ HTTP │   (Backend)     │ File │   (Config)      │
└─────────────────┘      └─────────────────┘      └─────────────────┘
     Port 3000               Port 3001           config-driven-dbt/
```

## Core Macro: `platform_entity()`

The heart of the system is the `platform_entity()` macro in `macros/platform_entity.sql`. It wraps user SQL with automatic control fields based on entity type.

### Usage Pattern

```sql
{{ platform_entity(
    entity_type='dimension',
    primary_key='customer_id',
    source_cdc_column='updated_at'
) }}

-- User writes only business logic
SELECT
    customer_id,
    first_name,
    last_name,
    email
FROM {{ ref('raw_customers') }}

{{ platform_entity_end() }}
```

### What Gets Generated

The macro transforms this into:

```sql
SELECT
    __user_query__.*,
    -- Platform Control Fields (auto-injected for dimension)
    MD5(CAST(customer_id AS VARCHAR)) AS _surrogate_key,
    CAST(updated_at AS TIMESTAMP) AS _valid_from,
    CAST('9999-12-31' AS TIMESTAMP) AS _valid_to,
    TRUE AS _is_current,
    CURRENT_TIMESTAMP() AS _loaded_at,
    'my_schema' AS _source_schema,
    'dim_customer_platform' AS _model_name,
    'abc-123-invocation-id' AS _dbt_run_id
FROM (
    SELECT
        customer_id,
        first_name,
        last_name,
        email
    FROM raw_customers
) AS __user_query__
```

### Control Fields by Entity Type

| Entity Type | Control Fields |
|-------------|----------------|
| **Dimension** | `_surrogate_key`, `_valid_from`, `_valid_to`, `_is_current`, `_loaded_at`, `_source_schema`, `_model_name`, `_dbt_run_id` |
| **Fact** | `_transaction_time`, `_ingestion_time`, `_source_system`, `_loaded_at`, `_source_schema`, `_model_name`, `_dbt_run_id` |
| **Bridge** | `_relationship_created_at`, `_is_active`, `_loaded_at`, `_source_schema`, `_model_name`, `_dbt_run_id` |
| **Snapshot** | `_snapshot_date`, `_snapshot_timestamp`, `_loaded_at`, `_source_schema`, `_model_name`, `_dbt_run_id` |
| **Staging** | `_layer`, `_loaded_at`, `_source_schema`, `_model_name`, `_dbt_run_id` |

## Frontend → API → dbt Flow

### 1. User Designs Entity in UI

The React frontend (`src/ClientMappingPortal.jsx`) provides a visual designer where users:
- Select entity type (dimension, fact, bridge, etc.)
- Choose source table from available seeds
- Map source columns to target columns
- Define primary key
- Configure relationships to other entities

### 2. API Receives Entity Definition

When the user clicks "Create Entity", the frontend POSTs to `/api/platform/entities`:

```javascript
// Frontend sends:
{
  "entityType": "dimension",
  "modelName": "dim_demo_test",
  "sourceTable": "raw_customers",
  "primaryKey": "customer_id",
  "description": "Customer dimension for demo",
  "columns": [
    { "sourceColumn": "email", "targetColumn": "email", "trackChanges": true },
    { "sourceColumn": "address_line1", "targetColumn": "address_line1" },
    { "sourceColumn": "city", "targetColumn": "city" }
  ],
  "relationships": [],
  "cdcConfig": {}
}
```

### 3. API Generates dbt Files

The Express API (`api/server.js`) handles this request:

#### A. Generate SQL Model File

```javascript
// api/server.js - generatePlatformModelSQL()
const sql = `{{
    config(
        materialized='table',
        tags=['platform_demo', '${entityType}']
    )
}}

{{ platform_entity(
    entity_type='${entityType}',
    primary_key='${primaryKey}'
) }}

SELECT
    ${columns.map(c => c.sourceColumn).join(',\n    ')}

FROM {{ ref('${sourceTable}') }}

{{ platform_entity_end() }}
`;

// Write to: models/platform_demo/dim_demo_test.sql
await fs.writeFile(sqlPath, sql);
```

#### B. Update Schema YAML

```javascript
// api/server.js - generatePlatformEntityYAML()
const entityYaml = {
  name: modelName,
  description: description,
  meta: {
    platform: {
      entity_type: entityType,
      primary_key: primaryKey,
      scd_type: 2,
      track_changes_on: columns.filter(c => c.trackChanges).map(c => c.targetColumn)
    }
  },
  columns: columns.map(c => ({
    name: c.targetColumn,
    description: `Column ${c.sourceColumn}`
  }))
};

// Append to: models/platform_demo/platform_demo.yml
```

#### C. Git Commit & Push

```javascript
await git.add([
  `models/platform_demo/${modelName}.sql`,
  'models/platform_demo/platform_demo.yml'
]);

await git.commit(`Add platform entity: ${modelName}`);
await git.push('origin', 'main');
```

## Schema YAML Structure (`platform_demo.yml`)

The schema file stores rich metadata that dbt and downstream tools can use:

```yaml
version: 2
models:
  - name: dim_customer_platform
    description: |
      Customer dimension with platform-managed SCD Type 2 handling.
    meta:
      platform:
        entity_type: dimension
        primary_key: customer_id
        business_key: customer_id
        scd_type: 2
        track_changes_on:
          - first_name
          - last_name
          - email
        relationships:
          - target: fact_orders_platform
            join_key: customer_id
            cardinality: one_to_many
            description: A customer can have many orders
    columns:
      - name: customer_id
        description: Natural key from source system
        tests:
          - unique
          - not_null
      - name: _surrogate_key
        description: Platform-generated surrogate key (MD5 hash)
      - name: _valid_from
        description: When this version became effective
```

### Key Metadata Sections

| Section | Purpose |
|---------|---------|
| `meta.platform.entity_type` | Tells macros which control fields to inject |
| `meta.platform.primary_key` | Used for surrogate key generation |
| `meta.platform.scd_type` | SCD strategy (1, 2, or none) |
| `meta.platform.track_changes_on` | Columns that trigger new SCD versions |
| `meta.platform.relationships` | Foreign key relationships for documentation |

## API Endpoints

| Method | Endpoint | Purpose |
|--------|----------|---------|
| `GET` | `/api/platform/entity-types` | Returns entity type definitions with control fields |
| `GET` | `/api/platform/sources` | Lists available seed files as source tables |
| `GET` | `/api/platform/sources/:table/schema` | Returns columns from a seed CSV |
| `GET` | `/api/platform/entities` | Lists existing platform entities from YAML |
| `POST` | `/api/platform/entities` | Creates new entity (SQL + YAML + git commit) |
| `DELETE` | `/api/platform/entities/:name` | Removes entity and updates YAML |

## Running dbt After Entity Creation

After creating entities through the UI, run dbt to materialize them:

```bash
cd config-driven-dbt

# Load seed data (if not already loaded)
dbt seed

# Run all platform demo models
dbt run --select tag:platform_demo

# Or run a specific model
dbt run --select dim_demo_test

# Test the models
dbt test --select tag:platform_demo
```

## Extending the System

### Adding New Entity Types

1. Update `ENTITY_TYPES` in `api/server.js`:
```javascript
const ENTITY_TYPES = {
  // ... existing types
  aggregate: {
    name: 'Aggregate',
    description: 'Pre-computed aggregate table',
    controlFields: ['_aggregation_level', '_computed_at', ...],
    icon: '📊',
    color: '#EC4899'
  }
};
```

2. Add control field logic in `macros/platform_entity.sql`:
```sql
{% elif entity_type == 'aggregate' %}
    {% do control_fields.append("'daily' AS _aggregation_level") %}
    {% do control_fields.append("CURRENT_TIMESTAMP() AS _computed_at") %}
{% endif %}
```

### Adding New Control Fields

Edit `get_entity_control_fields()` in `macros/platform_entity.sql`:
```sql
{# Add a new field to all entities #}
{% do control_fields.append("'" ~ target.schema ~ "' AS _target_schema") %}
```

## Troubleshooting

### Entity Created in UI but Not in Git

**Symptom**: Entity shows in the app but not in GitHub

**Cause**: Git push failed (usually authentication)

**Solution**: 
```bash
cd config-driven-dbt
git status  # Check for uncommitted changes
git push origin main  # Push manually
```

### Macro Errors When Running dbt

**Symptom**: `platform_entity is undefined`

**Cause**: Macro path not configured

**Solution**: Check `dbt_project.yml`:
```yaml
macro-paths:
  - macros
```

### Control Fields Not Appearing

**Symptom**: Model runs but no `_surrogate_key`, `_loaded_at`, etc.

**Cause**: Missing `platform_entity_end()` call

**Solution**: Ensure your model ends with:
```sql
{{ platform_entity_end() }}
```

## Architecture Benefits

1. **Self-Service**: Business users can create entities without writing code
2. **Consistency**: All entities get the same control fields automatically
3. **Governance**: Relationships and metadata are documented in YAML
4. **Auditability**: Git history shows who created what and when
5. **Extensibility**: Add new entity types or control fields in one place
